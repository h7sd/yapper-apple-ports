# Native authentication investigation

Checked 2026-10-31. Public HTTPS documents and shipped JavaScript were downloaded and inspected as inert text. No credentials were entered, no CAPTCHA was attempted, no account/application was created, and no browser cookies, local storage, or authenticated sessions were accessed.

## Approved implementation boundary

After this investigation the user explicitly approved a temporary web login: “ja web login hinzufügen alles andere NATIV”. The chosen implementation can therefore display the complete official login in a newly created, app-owned, nonpersistent WKWebView, allowing the official website to handle credentials, CAPTCHA and any additional authentication in one context. Chat and other application screens remain native. The CAPTCHA-only proposal below records the earlier alternative; it is not the selected flow.

The intentional app-session handoff is limited to successful authentication responses generated by the user's new sign-in inside that component. It must not import an existing browser/wrapper session or read storage, cookies, password fields or unrelated responses. The native API must verify the returned account and token identity, require completed MFA where applicable, and successfully bootstrap the account before persisting a session in Keychain. Cancellation must invalidate the pending attempt and prevent late callbacks from signing in.

## Observed

- The user's actual native login attempt returned a CAPTCHA-required error. The earlier public settings response without CAPTCHA fields therefore cannot establish that password sign-in is usable without a challenge.
- The official [developer documentation](https://yapin.gg/developers#login-with-yapper) describes authorization-code OAuth with PKCE for mobile/desktop apps. Its only scope is `identify`, which returns profile identity; messaging is expressly outside its scope. OAuth tokens use the `yo_` prefix, expire after 30 days, and do not have refresh tokens. Registered redirect URIs require exact matches and HTTPS, with HTTP loopback exceptions for development.
- The current [authorization page bundle](https://yapin.gg/_next/static/chunks/1m8y4dz9j4vbm.js) obtains the website's existing authenticated session, validates the client and redirect, and submits consent to `/api/oauth/authorize`. Its response redirects to the OAuth client. It does not expose a native full-chat session exchange.
- The upstream desktop `macos/upstream/main.js` maps `yapper://…` to a normal website path (lines 45–50). Its `yapin-discord` child window handles Discord server import (lines 272–284). Neither observed path establishes a native account-login callback.
- The current Capacitor bridge in [1-1_-_ebhezio.js](https://yapin.gg/_next/static/chunks/1-1_-_ebhezio.js) registers push, app navigation, status-bar, external-browser and screen-share integration. Its `appUrlOpen` handler routes website paths/channels/servers. No account-session handoff was identified in that examined module.

## CAPTCHA-only browser component: source-supported candidate

Final sign-in routing check on 31 October 2026: the anonymous root may display the marketing page. The official `https://yapin.gg/?auth=in` link selects the sign-in form through the website's own router. The root redirected to `www.yapin.gg`; the observed [root app chunk](https://www.yapin.gg/_next/static/chunks/2lxxd-jx-9d4l.js) reads the `auth` query, accepts `in`/`up`, selects the corresponding auth mode and removes the query with `history.replaceState`. SHA-256: `f49f9662e27c55bca8bd3c0463bf4ea8b671a3ee166ba706d3a5ba81dd12870f`. Version 0.1.1 starts at that official sign-in link; its bridge remains restricted to the root pathname.

The official sign-in UI is served from [the root page](https://yapin.gg/); `/login` returned HTTP 404 during this investigation. The current [login bundle](https://yapin.gg/_next/static/chunks/1jyoxkfup8hm2.js), module `77687`, mounts one normal CAPTCHA component with no `action` or `cData`. A second `signup_check` widget belongs to a conditional sign-up path and must not be confused with the login widget.

The CAPTCHA component, module `85665` in [0y078i2z__h10.js](https://yapin.gg/_next/static/chunks/0y078i2z__h10.js), waits for a pointer, keyboard, focus or touch interaction, loads the real `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit`, then calls `turnstile.render` on its `.captcha` container. Normal login uses automatic theme, flexible sizing and interaction-only appearance. Success supplies an ephemeral challenge response; expiry clears it, timeout resets the widget, and removal tears it down. The website's wrapper refuses its cached responses after 240 seconds.

The email login sends that response through Supabase `signInWithPassword` as `options.captchaToken`; the shipped SDK serializes it to `gotrue_meta_security.captcha_token`. Username login posts `{username, password, captchaToken}` to `/api/login`. Thus an ordinary native password request has an observed field for a user-completed challenge response; a browser authentication session need not be copied.

[Cloudflare's mobile documentation](https://developers.cloudflare.com/turnstile/get-started/mobile-implementation/) requires a browser component for Turnstile and describes WKWebView. Its [widget API](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/) supplies `getResponse`, `isExpired` and `reset`. The currently served `api.js` also explicitly implements an omitted-widget-ID branch for `getResponse()` and `isExpired()`; no private widget state is necessary to obtain the single login widget's public challenge response.

A narrowly scoped alternative could load the genuine HTTPS root page in an ephemeral WKWebView, let the user complete the visible verification, retrieve only the unexpired public challenge response, dismiss the sheet, and submit the existing native password request. In this alternative credentials would stay in the native form; the website form must not be submitted, because that could consume the response first. Restrict response access to the genuine trusted HTTPS main frame and the normal single-widget login state. Discard the response after one request, cancellation, or expiry. Do not load local HTML with a claimed remote base URL, generate challenges automatically, access browser sessions, or weaken CAPTCHA validation.

## Inferences and unresolved points

- The documented identity-only OAuth token cannot replace the Supabase access/refresh session required by the current native chat implementation. `ASWebAuthenticationSession` alone therefore does not establish a working full-client login under the examined contract.
- Strictly no browser component requires operator-supported native authentication, a registered full-chat handoff, or an appropriate additional OAuth capability. No such supported route was established in the inspected public scope; this is a bounded result, not proof that the operator has none.
- The CAPTCHA-only component is a candidate consistent with the observed request schema and provider guidance. It has **not** been verified against a real user-completed challenge/native password request. Device rendering, server acceptance, optional request binding, expiry/retry behaviour and account-specific authentication requirements remain to be tested by the user. Native application compilation does not prove live sign-in works.
