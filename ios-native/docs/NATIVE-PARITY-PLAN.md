## Account and security contract

The current settings lazy loader `91970` references `0mcrufu0avhsc.js`, `3i_zsv6of05h2.js`, `1y5-tms6m1pvx.js`, `27w8rh0cq5u7r.js` and `1sh49o-a95snt.js`. Existing passkeys use `my_passkeys`, `rename_passkey {p_id,p_name}` and `remove_passkey {p_id}`. Renaming is limited to 40 characters by the official form. Associated-domain support for native passkey creation is not established.

Connected OAuth grants use `oauth_my_grants` and `oauth_revoke {p_app_id}`. The rendered grant includes `app_id`, `name`, `owner_username`, `scope`, `first_at` and `last_at`. Do not confuse these identity-only third-party grants with the session needed for chat.

The shipped Supabase SDK in `1wdb3w49bvmss.js` implements TOTP enrollment as `POST /auth/v1/factors` with `factor_type: "totp"` and `friendly_name`; it reads `id` and `totp.qr_code`, `totp.secret`, `totp.uri`. Listing factors comes from the authenticated `GET /auth/v1/user`, not an admin endpoint. Removing one is `DELETE /auth/v1/factors/<id>`. Challenge and verify use the already documented factor-specific endpoints. A verified response replaces access/refresh tokens; native Keychain/session state must rotate before subsequent requests. The public [Supabase enrollment documentation](https://supabase.com/docs/reference/swift/auth-mfa-enroll) and [unenrollment documentation](https://supabase.com/docs/reference/swift/auth-mfa-unenroll) corroborate this provider contract.

The observed DM privacy setting updates the current `profiles` row's `dms_from` to `everyone`, `servers` or `friends`. Password changes use `POST /api/account/password {current,password}`; the official form accepts 6–72 characters. Global logout first signals `logout_everywhere_signal`, then calls auth logout with global scope. A complete per-device session-list endpoint was not established by the bounded source search; a current-login view must not claim to enumerate all devices.

## Acceptance evidence

Each implemented flow needs a native entry point, actual service calls, visible loading/error/permission states and meaningful transport tests. Offline fixtures must remain explicitly labelled and excluded from Release. Navigation must retain Yapper's visual identity, center the account surface at Pro Max sizes, support Dynamic Type and safe areas, and keep the official WebView confined to authentication. No role-gated UI establishes permission to perform a privileged server action.

Local source/fixture checks do not establish successful real-account login, live delivery, purchases, calls or physical-device behavior. Those verification limits remain explicit until corresponding evidence exists.
