# Yapper Native for iOS

A native iOS reconstruction in development, with **SwiftUI/UIKit application screens and native media**, plus a temporary WebView exclusively for official web sign-in. This is a separate application (`website.yapper.native.ios`) alongside the existing iOS client. It does not import any existing Safari, browser or wrapper session or replace the other client's installation.

The welcome screen shows Yapper's mark, a localized welcome title and sign-in action; terms/privacy links stay at the bottom. German and English follow the device's preferred supported language, with English fallback. The official page handles email/username sign-in, CAPTCHA and TOTP, then the temporary window closes. Conversation lists, paginated messages, text sending, incoming updates, account settings, keyboard handling and Dynamic Type remain native.

## Original-client UI reconstruction (0.2.1)

The user rejected the earlier generic iOS layout. This candidate replaces the main application shell with the original rail/sidebar/stage structure, mobile navigation, account bar and status menu. Friends, bottom profile overlays/editors, account/settings pages and the chat header/message/composer layout use native views with the shipped frontend's CSS geometry, original Inter variable font, original vector paths and source-derived avatar hash/status geometry. Chat beginnings, day dividers, the original seven-minute grouping conditions and source-sized empty/typed composers are included. The original message MP3 plays for eligible foreground unread DMs/groups; the profile sound switch, DND, hidden/muted chats, blocked senders and source throttles are respected. Existing call/media audio-session configuration is preserved. Background/server notification parity is not claimed. These are bundled native font/vector/audio resources; the product does not render the chat website in WebKit.

[Original UI evidence](docs/ORIGINAL-UI-SPEC.json) records stylesheet contexts and hashes; [profile/settings evidence](docs/ORIGINAL-PROFILE-SETTINGS.md) records their consumers. Source feature flags remain relevant: missing rollout flags do not justify showing every control. Anonymous offline reference renderings of the original React shell are comparison evidence, not proof of all account states or all screens. Some secondary management screens still retain native list/dialog structures. Global presence, source name-style/tint variations, several rollout-specific states and full Vencord/native call-interface parity remain incomplete or unverified. **This is not a claim of complete visual or functional 1:1 parity.** The 0.2.0 artifacts remain a separate historical build.

## Official web sign-in

Version 0.1.0 attempted direct native password login; the user reported a required CAPTCHA response. On 31 October 2026 the user approved the narrow web-login exception while keeping all chat screens native.

Version 0.1.1 opens the official sign-in link `https://yapin.gg/?auth=in` in a fresh, nonpersistent app-owned WebView. The website's own `auth=in` route selects its login form instead of the public marketing page. Credentials and verification are submitted by the user to Yapper's own page. A scoped bridge observes only fresh successful authentication HTTP responses from that login. It never reads passwords/request bodies, cookies, browser storage, Safari or another client's existing session. The native client validates the new session against Yapper's authentication server and current profile before saving it in its device-only Keychain. A verified second factor requires the corresponding higher-assurance session before entering native chats.

The website's authenticated chat UI is covered while the native session is being validated; success dismisses the web component. Cancellation/restart invalidates the attempt. Brief app switching for an authenticator is supported without permitting a background session commit. CAPTCHA is completed normally by the user; no solver, fake verification, forged origin or browser-identity spoofing is added.

**Real-account sign-in and live message delivery still require the user's device validation.** Automated tests use synthetic sessions; the public-page smoke check never submits credentials or CAPTCHA. Google/external-provider popup compatibility is not claimed; use email/username for this login flow. The official identity-only developer OAuth route does not grant chat access and is not substituted for a chat session.

See [the authentication investigation](docs/AUTH-HANDOFF-INVESTIGATION.md) and [observed API contract](docs/API-CONTRACT.md) for source evidence and limitations.

## Current development scope

The 0.2.0 development tree extends the earlier 0.1.1 DM preview. It includes native friends/requests/search/groups; inbox and profiles; profile editing and image cropping; message replies/edit/delete/reactions/pins and global/server/date search; attachments with the observed upload-and-scan sequence; voice recording/playback; polls and eligible public voter lists; bot buttons with private interaction replies; and native animated images, rich text and video playback. Server navigation includes permission-aware channels, roles, members, invites/applications, moderation, forums, events, emoji, webhooks, templates and audit tools, persisted folders/order and server/channel/category notification preferences. Account settings cover existing passkeys, OAuth grants, password and email-change requests, TOTP and account-data export/deletion. Community screens include shards/quests, leaderboards, cosmetic inventory, reports, suggestion submissions/voting and support. Apps and bot management include owned applications, redirect settings, scoped installations and explicitly confirmed credential resets; returned secrets are transient.

Voice/video and screen sharing use the pinned LiveKit native SDK. The observed Yapper media-key exchange has a separate CryptoKit implementation and a reproducible WebCrypto test vector. Joining starts muted; microphone/camera capture requires explicit user action. **Primitive cryptography tests do not establish successful interoperability with live Yapper calls.** On iOS 17–26, the current ReplayKit capture operates inside the app; a broadcast upload extension for full-device sharing is not included. On iOS 27+, the pinned SDK uses the native ScreenCaptureKit system picker. Audio routing, output volume, camera flipping, the official clip opt-out attribute and permission-aware voice moderation/reporting have native controls; reports currently contain text without recorded clips.

The five native plugin equivalents are character counter, image zoom, picture-in-picture, tracking-link cleanup and literal text replacement. They are native adaptations, not the original Discord plugin runtime. The original Vencord plugin catalogue cannot execute against native SwiftUI objects.

**Full 1:1 web parity is not complete.** The [92-area checklist](docs/native-parity.json) preserves missing/partial work and the historical 0.1.1 baseline. Native push registration, associated-domain support for new passkeys and native Plus checkout need operator/backend cooperation. Desktop process scanning, tray controls and global hotkeys require platform-specific treatment. Role-gated creator/staff consoles and several advanced integrations remain in the checklist. Implemented source and mocked tests are development evidence; real-account delivery, media, purchases and physical-device behavior remain unverified. The existing web-based client remains available during this work.

The official Windows installer was downloaded and inspected as the user's requested reference. It contains an Electron shell loading the remote web application, rather than a bundled copy of every chat screen. The [Windows evidence report](docs/WINDOWS-CLIENT-EVIDENCE.md) records installer/ASAR hashes and REA evidence. The [native parity plan](docs/NATIVE-PARITY-PLAN.md) separately records the public application dependency closure and its limits.

## Build

Open `YapperNative.xcodeproj` in Xcode. Xcode resolves the committed SwiftPM lockfile: LiveKit 2.19.0 and its pinned WebRTC/FFI dependencies. The project targets iOS 17 or later. Select your Apple development team to run on a physical device.

```sh
./scripts/build-native.sh simulator
./scripts/build-native.sh archive
SIMULATOR_ID=<dedicated-simulator-udid> ./scripts/build-native.sh test
```

The archive command produces an **unsigned IPA**. Sign it with your own Apple development/distribution profile before installing; it is not an App Store or TestFlight release. The Simulator ZIP runs only in Xcode's iOS Simulator. Optional project regeneration uses Ruby and `xcodeproj` 1.27.0: `ruby scripts/generate-project.rb`.

## Credentials and data

Session tokens use the app's device-only Keychain item. The official login page owns password entry; native account-security forms retain a password only while performing the requested account change. Account tokens never enter appearance preferences, app groups, an analytics system or the repository. Native REST requests use an ephemeral URLSession with cookies/cache/credential storage disabled and all redirects rejected. The temporary official sign-in WebView uses a nonpersistent website data store and normal TLS/WebKit behavior, separate from those native requests. Authentication and data requests are restricted to the observed service origins; TLS verification uses normal Apple defaults. The public anonymous Supabase project key is public client configuration, not a service-role key.

Signing out cancels pending operations, disconnects live updates and clears the local session and drafts. A separate explicit “sign out everywhere” action uses the observed service revocation flow; ordinary local sign-out does not claim global revocation. Messages and account details are sent to Yapper's own services as part of using the client. The privacy manifest declares access to the app's own appearance preferences under Apple's [UserDefaults API reason](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype); it is not a completed App Store privacy label or a claim about Yapper's backend data handling.

The original app mark and service identity retain their existing owners. The native implementation is an unofficial community client and is not endorsed by Yapper/Yapin', Vencord or YapBoard. No signing identity, private conversations or account sessions are included.
