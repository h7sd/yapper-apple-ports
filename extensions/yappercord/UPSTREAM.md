## Exhaustive coverage for this checkout

The upstream build's [`globPlugins`](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/scripts/build/common.mjs) enumerates `plugins/_api`, `plugins/_core`, `plugins`, and optional local `userplugins`. It skips hidden/underscore entries and root `index.ts` files, resolves directory `index.ts`/`index.tsx` files, and filters target suffixes according to the build kind. [`getPluginTarget`](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/scripts/utils.mjs) defines suffix interpretation; the [target type list](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/utils/pluginTargets.ts) defines recognized tags.

This catalog takes the union of every official source entry across those target gates, so it includes entries that a single desktop or web build excludes. It contains **186 entries: 167 public plugins, 14 API components, and 5 core components**. Fifteen entries carry a target suffix. Optional local third-party userplugins are outside the selected upstream tree. The upstream [public-list generator](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/scripts/generatePluginList.ts) omits `_api`; this inventory includes those internal build entries explicitly, rather than presenting them as additional user-facing features.

The generator parses static name/description strings and `Devs.NAME` references to the [published author constants](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/utils/constants.ts). It preserves unresolved conditional flags as null plus the source expression. It never evaluates such flags. Source metadata with a changed or ambiguous literal format fails closed. Metadata/property parsing is intentionally narrower than a general TypeScript parser.

Coverage is checked in two ways: snapshot counts/provenance/metadata assertions, and an independent selection from the pinned Git tree followed by exact regeneration when `VENCORD_SOURCE` is supplied. The committed catalog records the inventory fingerprint and hashes of its selection and author sources. Nine tests passed with the explicit pinned checkout, including full-source comparison.

## Why the original plugin files need porting

Vencord's [`PluginManager`](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/api/PluginManager.ts) consumes `definePlugin` objects, registers commands/UI hooks, invokes message pre-send/pre-edit handlers, attaches Flux listeners, and supplies patches to its webpack patcher. Its [patcher](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/webpack/patchWebpack.ts) intercepts Discord module factories and applies source find/replacement definitions. These contracts refer to Discord's module registry, React components, Flux events, stores, and compiled bundle contents. Yapper's live responsive website supplies a different application and module graph.

The catalog records concrete source locations for each blocker, not only a plugin-name classification. In this checkout:

- **146 entries** declare bundle patches.
- **123 entries** declare non-explicitly-type-only `@webpack` imports.
- **38 entries** import Vencord's Discord utility module.
- **5 entries** declare patched message lifecycle hooks.
- **9 entries** include an upstream `native.ts` helper.
- **161 of 167 public plugins**, or **179 of 186 total entries**, have at least one of the four inspected direct Discord binding forms: webpack imports, bundle patches, Discord utility imports, or message lifecycle hooks.
- **66 entries** reference Discord type packages. These are recorded separately: a type import may be erased by TypeScript and is not proof of a runtime dependency.

Every entry also exports the Vencord plugin contract. The six public entries outside the direct-binding union—F8Break, FixSpotifyEmbeds, FixYoutubeEmbeds, NoMiddleClickPaste, oneko, and YoutubeAdblock—are not thereby proven portable; their source can still require native IPC, Discord selectors, browser quirks, or host lifecycle changes.

`signals` are lexical observations scoped to the entry and its own code/CSS helper files. Comments and string contents can match token searches; indirect imports can add further dependencies. The `blockers` array supplies exact source paths, line numbers, and declared import/patch/hook evidence for the principal porting boundaries. These observations justify host-specific implementation work; they do not prove runtime activation, behavior, universal incompatibility, security, or a complete transitive dependency graph.

## Six bounded implementation candidates

These source-derived feature ideas can be reimplemented using browser DOM APIs and explicit user actions. The Yapper runtime gives them separate adaptation descriptions and capability checks; their original catalog records retain `requires-port`.

1. **CharacterCounter.** [Upstream source](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/plugins/characterCounter/index.tsx) renders text/selection counts using patched Discord editor props and UserStore premium limits. A Yapper adaptation can count text in an identified message composer. Discord's 2,000/4,000 premium limit must not be asserted as Yapper's limit; use an observed editor limit or show only the actual count.
2. **ClearURLs.** [Upstream source](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/plugins/clearURLs/index.ts) downloads provider rules and transforms Discord pre-send/pre-edit message objects. A bounded Yapper adaptation can offer explicit cleaning of known query tracking keys in a text workbench or supported textarea. It does not reproduce all provider-specific rules, guarantee tracker removal, or silently hook unknown rich-text send internals.
3. **ImageZoom.** [Upstream source](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/plugins/imageZoom/index.tsx) patches Discord image components and provides a configurable magnifying lens/context menu. An explicit gallery or Shift-click view of already visible, meaningful images uses ordinary DOM APIs. It is a smaller feature than the complete upstream magnifier and must preserve alt text, keyboard closing, and safe URL handling.
4. **PictureInPicture.** [Upstream source](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/plugins/pictureInPicture/index.tsx) patches a Discord media toolbar and uses a cloned video. A Yapper adaptation can request PiP for a selected visible video only when the browser exposes a supported API. System permission, media state, user activation, WebKit differences, and a rejected request remain real constraints.
5. **NoF1.** [Upstream source](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/plugins/noF1/index.ts) removes Discord's F1 binding through a bundle patch. A foreground DOM key handler can suppress an F1 event in the Yapper document. It is not a global keyboard hook and has no promised effect on operating-system shortcuts or a keyboard that does not send F1.
6. **TextReplace.** [Upstream source](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/plugins/textReplace/index.tsx) includes saved simple/regex rules and modifies Discord messages before send. A Yapper adaptation can apply saved literal rules on an explicit user command and leave the result for review. Unsupported controlled rich editors need a copy/paste workbench; message transmission and arbitrary regex execution are separate capabilities.

Three initially plausible examples need stronger host evidence. [BiggerStreamPreview](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/plugins/biggerStreamPreview/index.tsx) obtains previews through Discord streaming stores, so a visible-image enlarger does not establish preview retrieval. [BlurNSFW](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/plugins/blurNsfw/index.ts) patches the Discord channel's `nsfw` state; guessing sensitive Yapper channels from text or image content would not reproduce that contract. [NoTrack](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/plugins/_core/noTrack.ts) patches Discord analytics/metrics and hooks its Sentry initialization. A Yapper privacy control needs actual endpoint and behavior evidence; copying Discord-specific prototype setters does not establish that Yapper tracking has been disabled.

## Installer boundary

The upstream installer is a Go GUI/CLI targeting Discord installations. Its [macOS discovery code](https://github.com/Vendicated/VencordInstaller/blob/595991ca27520868af4f9c48adf0c53ee971f1f2/find_discord_darwin.go) finds Discord.app/PTB/Canary/Development bundles in application locations. The [patcher](https://github.com/Vendicated/VencordInstaller/blob/595991ca27520868af4f9c48adf0c53ee971f1f2/patcher.go) renames `app.asar` to `_app.asar` and writes an injection archive. [`WriteAppAsar`](https://github.com/Vendicated/VencordInstaller/blob/595991ca27520868af4f9c48adf0c53ee971f1f2/app_asar.go) creates an entry that requires the downloaded patcher. Its [downloader](https://github.com/Vendicated/VencordInstaller/blob/595991ca27520868af4f9c48adf0c53ee971f1f2/github_downloader.go) obtains upstream build assets. These are source observations; this investigation did not run them.

Vencord's [desktop injection entry](https://github.com/Vendicated/Vencord/blob/644434941b515a2626a2161e219653cb36e723e7/src/main/patcher.ts) restores Discord's original app entry, substitutes a preload, and configures its native layer. A Yapper client installer needs a Yapper-specific build/package flow. The upstream Discord search/ASAR injection scheme does not install plugins into a WKWebView iOS bundle or establish compatibility with Yapper's Electron bridge. Any Yapper installer supplied alongside this folder must state what it copies/builds and preserve the original client/native permission boundaries.

Whether a particular integration forms a combined covered work depends on its technical relationship; merely naming a file a “plugin” does not decide that boundary. The [FSF's plugin/combined-work FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#GPLPlugins) explains its interpretation. Publication must satisfy the licenses of the actual distributed combination; this document does not settle an unreviewed host-license question or certify store-distribution compatibility.
