# Security review and verification limits

This document records a bounded review of the macOS desktop shell and the checks this repository can reproduce. It does not certify that Yapper, its upstream AppImage, third-party packages, or its live website is malware-free. It cannot guarantee the absence of a remote-access trojan, a vulnerability, malicious future server content, or a compromised dependency.

## What was reviewed

The reviewed macOS application-owned source is `macos/main.js`, `macos/preload.js`, `macos/mac-processes.js`, and `macos/games.js`, together with packaging configuration and tests. `macos/upstream/` preserves the recovered originals and manifest. `macos/provenance.json` records input and source hashes. The original REA analysis was static and selected the app-owned files; it did not inspect every dependency or fully decompile the native runtime. Raw logs containing local workstation paths are omitted from the public tree; see `macos/evidence/README.md`.

The initial Electron 38.8.6 Apple Silicon app was smoke-tested for startup, live-service loading, its sandboxed bridge, settings, running-program enumeration, badges, menu zoom, hide/reopen, and an invite route. That test did not place a real call, record media, grant Accessibility, or exercise a real login cycle. The updated runtime is verified separately for the public release. The Intel package is built and checked structurally, not run on Intel hardware. Historical observations are separate from future CI results.

## Native capabilities and data exposed to the website

- **Remote content and authentication:** the main window loads `https://www.yapper.website`. The service, account flows, messages, and renderer JavaScript remain controlled by the upstream service and can change without a new desktop binary.
- **Trust-host checks:** navigation, most IPC handlers, and permission checks accept HTTPS URLs on `www.yapin.gg`, `yapin.gg`, `www.yapper.website`, `yapper.website`, `rt.yapper.website`, and `lk.yapper.website`. This is a hostname check; it does not constrain HTTPS ports. It is not a network egress allowlist: permitted pages can load external resources and make their own network requests.
- **Renderer separation:** the main window and Discord-import popup declare `sandbox: true`, `contextIsolation: true`, and `nodeIntegration: false`. The preload exposes named `yapperDesktop` methods rather than a generic shell, filesystem, or arbitrary IPC execution API. The version IPC returns the application version without an origin gate; the more privileged handlers use `fromYapper`.
- **Microphone, camera, and notifications:** trusted pages can request them. macOS media permission is requested for the device the page names. Once OS consent exists, the website controls use through the allowed web APIs. Trusted-host permission checks also permit display capture, clipboard read/sanitized write, and fullscreen.
- **Screens and window thumbnails:** trusted pages can enumerate sources and receive window/screen names, thumbnails, and icons. A selected source lasts for one request within 30 seconds. The display-capture handler falls back to the first available screen if there is no valid fresh selection, disables the system picker, and does not independently require `req.userGesture`. Therefore, OS screen-recording permission is a significant trust grant; the desktop code does not enforce a new native confirmation for every capture request. Mac system-audio loopback remains disabled after the runtime update.
- **Application activity:** activity detection is enabled by default. Every 20 seconds, the native process queries running GUI applications through a fixed local `osascript`/NSWorkspace program, with a fixed `/bin/ps -axo comm=` fallback. It matches executable identities to known/custom games and forwards the selected activity name and start time. The website can also request up to 80 filtered executable/display-name entries for its game picker. The full executable paths used internally are not returned by that bridge method. Users can disable activity in desktop settings.
- **System idle time:** the main process forwards seconds since system-wide keyboard/mouse activity to the renderer every 15 seconds. This is broader than activity within Yapper alone.
- **Global hotkeys:** `uiohook-napi` is a native system-wide input hook. On Mac the app checks Accessibility trust before loading/starting it. Current app-owned handlers compare configured keys/buttons and forward push-to-talk booleans or mute/deafen actions while the Yapper window is unfocused; no typed-text buffer or general key-event upload was found in those handlers. The renderer chooses the key configuration and when it is active; the main process does not independently verify that a call is running. This is an observation about reviewed source, not a complete audit of the native dependency or future website behavior.
- **Local state and persistence:** settings and zoom are written beneath Electron's user-data directory. The Electron profile also stores normal website session data. Close-to-background is enabled by default. Trusted pages can change the Open at Login setting through the settings bridge; the macOS login-item mechanism may require OS approval.
- **External applications and commands:** ordinary external web/mail links open with the system browser/mail handler. Native Help commands open fixed macOS privacy panes. Process enumeration uses fixed executable paths and argument arrays through `execFile`, without constructing a shell command from website text. This is not an App Sandbox application: Electron renderer sandboxing does not sandbox the Node main process.

## Updates, signatures, and dependencies

Automatic binary downloads and background update checks are disabled on macOS because this port has no signed Mac update feed. The shipped `electron-updater` dependency remains pinned for provenance, and manual downloads open the upstream site. This does not freeze the live website or prevent the website from changing its desktop-bridge calls.

The public release pins Electron **`45.1.0`**, `@electron/packager` `20.3.0`, `electron-updater` `6.8.9`, and `uiohook-napi` `1.5.5` with an npm lockfile. The recovered upstream runtime was Electron `38.8.6`; its identity remains in provenance. The public port deliberately updates that runtime before release. `npm ci` downloads dependencies and runs their lifecycle scripts, including Electron acquisition. npm integrity hashes help identify package bytes but do not prove package intent or safety. The CI advisory report must be inspected separately from build/test success; advisory databases can be incomplete or unavailable.

Before the update on **2026-10-30**, `npm audit --json` reported **two vulnerable packages, both high severity**: `electron` and its installation dependency `extract-zip`. This is a package count, not a count of all underlying advisories. Electron's entry included multiple runtime advisories, including [a context-isolation bypass affecting Promise-returning contextBridge APIs](https://github.com/electron/electron/security/advisories/GHSA-h7rp-cf8h-j98x) and [iframe permission-origin attribution](https://github.com/electron/electron/security/advisories/GHSA-9pf5-hg6p-4pwp). The reviewed preload does expose Promise-returning bridge methods. Applicability and exploitability depend on the complete application/service scenario; these checks did not attempt exploitation. The port was upgraded to the official Electron `45.1.0` release rather than publishing the vulnerable exact-runtime package. [Electron's own security guidance](https://www.electronjs.org/docs/latest/tutorial/security) recommends current framework releases.

After the update on **2026-10-30**, a complete `npm audit --json` reported **zero vulnerable packages**, and `extract-zip` was absent from the installed dependency tree. The production-only audit also reported zero. These are results from the npm advisory database at that time, not a guarantee that every vulnerability is known or absent.

The earlier production-only audit also reported zero before the fix. That narrower result **excludes Electron because the npm manifest lists it as a development dependency, even though Electron is shipped in the app**. It must not be used as a substitute for the complete audit. The CI audit step is explicitly nonblocking so a build can be inspected alongside any future advisory inventory; it is not a malware scan or security clearance.

Builds use ad-hoc signatures and hardened-runtime entitlements for Electron, camera, microphone, JIT, unsigned executable memory, and disabled library validation. They are not Developer ID signed or Apple notarized, and the main process is not App Sandbox restricted. An ad-hoc signature supports local code-integrity checks; it does not establish publisher identity, endorsement, or harmless behavior. SHA-256 checksums identify an archive relative to the published value; a compromised release channel could replace both.

## Reproducible checks

`node scripts/verify-macos.mjs` checks syntax, selected renderer/IPC/update invariants, pinned versions, and upstream hash relationships. `npm test` in `macos/` exercises mocked Electron flows and process-parser regressions; one Mac test performs a read-only NSWorkspace enumeration. These are selected checks and can miss defects or malicious behavior outside their assertions.

After a build, `node scripts/verify-macos.mjs --arch=arm64` or `--arch=x64` extracts the archive into temporary non-synced staging, verifies nested code signatures and executable/native-module architecture, compares packaged source bytes to the current source, checks excluded development files, and writes an archive checksum and a sanitized JSON report. It does not launch the app or grant native permissions.

The macOS workflow uses commit-pinned official GitHub Actions, read-only repository permissions, no release publication, no signing secrets, and no `pull_request_target` execution. It uploads builds, checksums, reports, and advisory results as temporary CI artifacts. A green workflow means its selected checks passed. Review the exact commit, build logs, advisory output, and limitations before deciding whether to run a build or grant native access.

## Remaining review gaps

There has been no exhaustive native-code audit, independent remote-service audit, sustained network capture of real calls, penetration test, or fresh third-party malware-lab assessment. No conclusion is made about all upstream dependencies, future service content, credential handling inside the remote service, or behavior after every native permission has been granted. Any changed trust host, preload method, IPC handler, permission handler, native dependency, update path, or entitlement needs renewed review.
